## Design — this is the "Radar Macro" theme, not Mambrini's

Rodrigo explicitly asked to reuse the theme already built for the Artifact dashboard (**not** Mambrini's light navy/serif editorial look). After seeing it render light in his own (light-OS) Chrome, he then explicitly asked for a **fixed, always-dark** identity, GitHub-dark-flavored — so `css/style.css` `:root` is now a single committed dark palette (`#0D1117` bg / `#161B22` surface / `#E6EDF3` text), no `@media(prefers-color-scheme)` or `[data-theme]` branching. **Don't reintroduce a light mode or OS-adaptive theme** without asking first — that's what caused the confusion. `site/dashboard_template.html` (the Artifact build) was patched to the same fixed palette for parity.

- **Type**: `Fraunces` (display — tab tickers, section headings), `IBM Plex Sans` (UI/body), `IBM Plex Mono` (all numbers — prices, dates, axis ticks; use the `.num` class).
- **Color**: one dark palette, painted explicitly (see above) — no theme switching logic anywhere. Per-asset accent hues are deliberately ordered `EWZ` (green) → `FXE` (blue) → `EEM` (magenta) — that order is load-bearing: it's the only ordering of those 3 hues that clears the CVD-safety adjacency check (validated by hand against `dataviz` skill's `validate_palette.js` logic, since Node wasn't available — ran the same math via the browser's `javascript_tool` instead). **Don't reorder the tabs** without re-checking that.
- Status colors (`--good` / `--warning` / `--critical`) are separate from the per-asset accents on purpose — don't reuse an asset's accent color to mean "good/bad".

## Chart ranges

`js/app.js`'s `RANGES` array: `1D` (intraday, 5-min bars), `1S`/`1M`/`6M`/`1A`/`3A`/`5A` (daily-data slices), `Max`. Default is `1M` (`DEFAULT_RANGE_KEY`).

- **1D is fundamentally different from the rest**: `scripts/fetch_and_compute.py`'s `fetch_intraday()` pulls Yahoo's `range=1d&interval=5m` separately per asset and stores it as `assets.<SYM>.intraday.{times, close}`. The Performance and Drawdown charts render it fine (indexed to the prior close). **Rolling vol/Sharpe cannot be shown for 1D** — they're 21-/63-*trading-day* windows, meaningless on 5-minute bars — so those two chart cards show a text placeholder (`.intraday-note`, toggled via `renderCharts()`) instead of a canvas whenever `range.intraday` is true. Don't try to compute an "intraday Sharpe"; it doesn't mean anything with this method.
- Every other range just slices `dates`/`close`/`drawdown_pct`/`rolling_vol_pct`/`rolling_sharpe` from the daily arrays — no new data needed.

## Cache-busting

`js/app.js`'s `loadData()` appends `?t=${Date.now()}` to both JSON fetches, on top of `cache:"no-store"`. This isn't redundant: `cache:"no-store"` only controls the *browser's* cache, but GitHub Pages is served through a CDN (Fastly) that can still return a cached response for the same URL — the query-string bust forces a distinct URL so the CDN can't shortcut it. Keep both.

## Interpretations logic (`js/interpretations.js`)

Historical context bands (`bands.sharpe`, `bands.vol` in `etf_data.json`) are **real percentiles (p10/p25/p50/p75/p90) computed over each asset's own loaded history** by `fetch_and_compute.py` — not hardcoded guesses. If you add a new interpreted metric, compute its band server-side the same way rather than eyeballing a "normal range".

## The "Fundo" page

A second static page (`fundo.html` / `js/fundo.js` / `css/fundo.css`), added after Radar Macro, simulating a fixed R$100M buy-and-hold long-only fund: 40% EWZ / 35% EEM / 25% FXE, share counts fixed at `data/fundo.json`'s `inception_date` (2026-09-04) — **no rebalancing, ever**. Linked from a new shared `nav.site-nav` bar (in `css/style.css`) that now sits above both pages.

- **`data/fundo.json` only holds the fund's fixed definition** (capital, entry weights, entry prices, inception date) — it does **not** store a growing price history. `js/fundo.js` derives the fund's entire NAV/return/drawdown/rolling-vol/rolling-Sharpe series client-side from `data/etf_data.json`'s existing daily `close` arrays (filtered to `>= inception_date`) and its per-asset `intraday` field (for the 1D view). This means the Fundo page updates automatically every time the existing hourly Actions workflow refreshes `etf_data.json` — **no second data pipeline was added**, and none should be, since NAV = fixed shares × that day's close is a pure function of data Radar Macro already fetches. If you're tempted to add a `fund_history` array to fundo.json or a second GitHub Action for it, don't — recompute from etf_data.json instead.
- Rolling Sharpe (63d) / vol (21d) are computed **since inception**, not over multi-year history like Radar Macro — so for weeks after launch they'll correctly show "aguardando historico (Nd/63 pregoes)" instead of a number. That placeholder is intentional (see `insufficientNote()` in `js/fundo.js`); don't backfill it with Radar Macro's long-run stats, they'd describe a different measurement window.
- The "Metricas detalhadas" table compares the fund against each of the 3 assets **using that same since-inception window**, for a fair like-for-like comparison — not against the assets' full historical stats shown on Radar Macro.
- Currency: capital is labeled "R$" per Rodrigo's spec, but no BRL/USD conversion is applied anywhere — capital and the USD ETF prices are treated as the same unit purely for this simulation's arithmetic. Don't silently "fix" this by inserting an FX rate; ask first if it matters.
- **CDI benchmark line** (performance chart only): fetched from the Banco Central SGS API (`bcdata.sgs.12`, daily % rate) by `fetch_cdi()` in `scripts/fetch_and_compute.py`, stored as `etf_data.json`'s top-level `cdi: {dates, daily_rate_pct}` — **not Yahoo Finance**, CDI isn't a traded instrument with a price. `js/fundo.js`'s `buildCdiSeries()` compounds it into an index starting at the fund's inception date and forward-fills it onto the fund's own trading-day calendar (BCB's calendar and NYSE's don't perfectly match). BCB typically lags ~1 business day, so the CDI line's most recent point(s) may sit flat until it catches up — that's a data-availability artifact, not a bug. No CDI line on the 1D/intraday view: CDI is published once a day, so an "intraday CDI" would be fabricated.
- "Analise macro" / "Leitura do fundo" section is a deliberately empty placeholder (card + explanatory text, no data file) — Rodrigo said it'll be filled in later. Leave it empty until asked.

## The "Medidas Econometricas" page

Third static page (`medidas.html` / `js/medidas.js` / `css/medidas.css`): correlation heatmap, a 3-slider long-only portfolio simulator, an efficient-frontier scatter, and a max-Sharpe (Markowitz) recommendation for EWZ/FXE/EEM. Same pattern as Fundo — no new data file beyond what's needed for definitions, everything derived client-side from `data/etf_data.json` (daily `close` arrays + `cdi`).

- **Single consistent window**: correlation, the covariance matrix, and each asset's "expected return" (annualized from realized total return) are ALL computed over the same `WINDOW = 63` trading days (`js/medidas.js`). This was a deliberate simplification for internal consistency — don't compute correlation over one window and expected return over another without a reason.
- **Expected return is a noisy trailing-realized-return estimate**, stated as such in the disclaimer banner and footer. Because of this, when one asset has had an outsized recent rally (e.g. EWZ's run in Aug/Sep 2026), the Markowitz optimizer can legitimately land on 100% of that asset — mean-variance optimization on trailing returns does this. **That is correct behavior for the stated methodology, not a bug** — don't "fix" it by capping weights or blending in a longer window unless asked; the disclaimers exist precisely because of this failure mode of naive historical-return inputs.
- **rf (risk-free rate) = CDI, not Selic**, despite the original spec saying "Selic do dia" — this project already fetches CDI (not Selic) for the Fundo page's benchmark, and the two are economically near-identical in Brazil's "CDI over" convention. Reusing it avoids a third BCB series/pipeline. Said explicitly in the footer; don't silently add a Selic fetch without asking.
- **Efficient frontier = a long-only grid search**, not a closed-form quadratic solve: `FRONTIER_STEP = 0.02` over the 3-asset simplex (integer loop counters, not `+=` float accumulation — that produced `-0%` weights the first time around, from float drift after ~50 additions). The same grid's best-Sharpe point *is* the plotted Markowitz optimum — there's no separate optimizer. Raising precision means lowering `FRONTIER_STEP`, which grows the grid roughly quadratically; 0.02 (~1300 points) is already comfortably fast client-side, no caching/interval-recompute was added since there's no real perf problem to solve (nothing is fetched, it's a few thousand 3x3 matrix products in JS, computed once on load).
- **Diversification index** = normalized effective-number-of-bets on the Euler risk-contribution decomposition: `ENB = 1/sum(contrib_i^2)`, `DI% = (ENB-1)/(N-1)*100`. 0% = risk fully concentrated in one asset, 100% = each asset contributes equally to portfolio risk (not the same thing as equal *weights*).
- No CDI line/point on this page (unlike Fundo's performance chart) — the frontier axes are risk/return, and CDI has ~zero volatility on this scale, which would sit degenerately at the vol=0 edge rather than add insight.

## Known limitations / things to revisit

- Yahoo Finance's chart API has no official CORS allowance for arbitrary browser `fetch()` — that's exactly why prices are fetched server-side (GitHub Actions / the Python script) rather than client-side on page load. Don't try to add a client-side "refresh now" button that hits Yahoo directly; it'll be blocked for most visitors.
- Sharpe assumes **rf = 0%**, stated in the footer — not a real risk-free rate. Fine as a relative/rolling indicator, wrong if anyone asks for an absolute Sharpe number.
- `data/thesis.json` currently drifts between the two deployments until the routine is updated to push here too (see Data pipeline above).
- Repo is **public** — never commit anything from `JGP Cupula*.xlsx` or other personal/desk files; `.gitignore` already excludes the xlsx by pattern, keep it that way.
